# Validation and limits

The browser target is Firefox 158.0 on macOS. Browser checks were performed only in a disposable test profile. Normal browsing profiles and the Zen installation were not used. This record describes targeted checks, not a guarantee for every Firefox version, theme, platform, or extension.

## Current address bar and New Tab behavior

The floating New Tab hook and the centered address-bar CSS have both been removed. Earlier removal checks covered only command interception; the remaining CSS still moved the focused address bar over the page. The address field and its native suggestions now retain Firefox’s toolbar positioning. The former script filename remains only as compatibility cleanup for existing loaders; it unloads an active older hook and installs no command wrapper, listener, or wake observer. Managed updates replace the old script without application changes. Earlier floating-search checks below describe the retired implementation, not a current feature.

In the isolated profile, an active copy of the previously shipped hook was unloaded, restoring native command and URL submission implementations. Seven entry checks passed: both command IDs, the File menu command, direct native action, real Command+T, a real sidebar click, and sidebar keyboard activation after ten compatibility-file reloads. Each created one regular tab and preserved the source page; address submission used the created tab without adding another. The other three features loaded, no window errors were captured, and test settings/windows were restored. [Removal checks](validation/newtab-retirement.json).

The remaining floating-CSS defect was reproduced by loading the previous stylesheet: the focused address bar computed to `position: fixed` over the page. With that entire block removed, real Command+L and Command+T kept the address bar within the toolbar in all four normal/compact combinations (eight cases), with native `position: relative`. Normal New Tab creation remained intact. The toolbar placement was also visually inspected with suggestions open. [Docked address-bar checks](validation/docked-address.json).

## Fullscreen toolbar fix

The previous stylesheet still applied a 44px minimum toolbar height and 2px vertical padding while Firefox collapsed the toolbar for page fullscreen. A native fullscreen request in the test profile confirmed that the hidden nav bar retained 4px of padding; the page itself already started at y=0 in that headless reproduction, so the exact macOS white strip was not reproduced.

Page fullscreen now bypasses the foundation layout overrides and explicitly removes the toolbox from layout and painting. Ordinary browser fullscreen retains Firefox's own toolbar sizing, padding and painting. Eight focused checks covered real page-fullscreen entry/Escape and browser-fullscreen address-bar access in all four compact configurations. The page reached y=0, toolbox and nav-bar rectangles were zero, and the first 20 rows of a black fixture contained no white pixels. Exiting page fullscreen inside browser fullscreen restored the native toolbar; normal-window sizing returned after exit. No fixture window errors were recorded. This was a headless Firefox 158/macOS test; physical macOS menu-bar auto-hide was not tested or changed. [Measurements](validation/fullscreen-toolbar.json).

## Tab scrolling and canceled-drag recovery

The previous hierarchy code pulled an offscreen selected tab back into view after every refresh: the reproduction moved from scrollTop 766 to 66. Refresh now preserves a visible selection through layout changes without pulling a manually scrolled list back. Explicit priority changes and sidebar expansion can still reveal selection; a pending reveal also yields if the scroll position changed in the meantime.

The native regression used 100 disposable blank tabs, four Favorites, sixteen pinned rows, three folders and one split pair. Real wheel input scrolled ordinary and pinned lists in both directions at 180/240/300px widths, expanded/collapsed layouts and 768/500px window heights. Twenty refreshes preserved each manually scrolled position. Native selection, real tab clicks, normal New Tab, horizontal orientation and ten script reloads passed. Opening background tabs also scrolls the native Firefox baseline toward the new tab; that opening policy remains native, and subsequent wheel scrolling/refresh stays usable.

Controlled canceled priority-drag state resumed updates after real window switching and a fresh tab click. Real split-preview DOM construction survived its native tab switch and was removed on deactivation or a new tab click. Only the fixture exposes those setup callbacks; production has no diagnostic API. Using the focus manager's active window avoids treating transient document blur during tab switching as deactivation. Six automated lifecycle cases cover missed dragend, focus distinctions, release outside the strip, source close/pin, fifty cancellation cycles returning to five idle listeners, and uninstall. No window errors were captured by the native fixture. These headless checks do not certify physical OS drag release or every third-party extension. [Measurements](validation/tab-scrolling.json) and [Zen source comparison](ZEN-SCROLLING.md).

## Performance changes

## Retired floating-search focus and wake recovery (historical)

The old hook canceled the floating New Tab search when macOS returned focus to the page. Recovery now preserves the draft, native search mode, and selection through temporary window blur/deactivation, minimize/restore, and sleep/process-resume notifications. macOS can blur/refocus a window without a matching deactivate/activate pair; the native reproduction covered that path.

Six real two-window focus cycles and native minimize/restore retained a bookmark-search draft and backward text selection. Twenty simulated sleep/wake cycles called only this hook's observer, avoiding global browser or OS sleep effects. Recovery did not focus a background window. Escape, Command+L, an outside pointer event, tab switching, navigation, and uninstall canceled pending restoration; submission after recovery created exactly one new tab and preserved the source page. Thirty lifecycle cycles returned to two idle listeners and zero power observers; uninstall removed every hook. No window errors were captured. [Recorded results and source hash](validation/search-wake.json).

The 14 new automated cases cover these races, coalesced wake signals, synchronous focus during native view teardown, process resume, and cleanup. **Physical operating-system sleep was not forced**, so these checks do not certify every hardware wake sequence. The existing UI regression was rerun against the changed hook, including search-mode restoration, settings, hierarchy, large-tab scrolling, and both split-drop directions.
